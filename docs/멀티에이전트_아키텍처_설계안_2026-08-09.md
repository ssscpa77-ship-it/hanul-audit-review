## 1. 문제 정의 — 왜 멀티에이전트인가

현재 hanul-002는 「L1 규칙엔진 → (선택)L3 AI 서술 → 후처리」로 이어지는 **단일 순차 파이프라인**이다.
규칙엔진은 계정 9종의 `PROCEDURE_RULES`와 키워드 1개 매칭 수준의 절차 탐지에 머물러 있고, AI 리뷰는
시트 단위로 1회 호출되어 조서 전체를 얕게 훑는 구조다. 「자가검토_작업지시서_전체설정」§6 Gap표가
스스로 지적하듯, 다음 네 가지가 구조적 한계로 남아 있다.

| Gap | 현상 | 근본 원인 |
|---|---|---|
| #5 | 절차 탐지가 키워드 1개 통과로 완료 | **판정 로직이 얕음** — 필수 키워드 세트·증빙 구조를 보지 않음 |
| #6 | 절차 카탈로그가 9계정에만 존재 | **계정별 전문성이 코드화되지 않음** — 나머지 계정은 KB 검색에만 의존 |
| #17 | 감리지적사례가 기존 노트 보강([사례인용])에만 쓰임 | **사례 DB → 조서 역매칭(선제 탐지) 로직이 없음** |
| #18 | 절차 완전성이 "흔적 발견" 수준 | **표준감사프로그램 단위 Pass/Fail 판정이 없음** |

이 네 가지는 각각 "계정 전문성 부족", "절차 완전성 검증 부재", "리스크 사례 매칭 부재",
"계산·상호참조 정합성 검증 부재"로 요약되며, **하나의 범용 규칙엔진·하나의 범용 AI 호출**로는
구조적으로 해결되지 않는다. 각 문제 영역을 전담하는 **전문화된 에이전트**가 병렬로 조서를 검토하고,
그 결과를 상급 심리역(오케스트레이터)이 통합·조정하는 구조 — 즉 실제 회계법인의 **"계정 담당자 +
QC 심리역 + 파트너"** 협업 방식을 소프트웨어로 재현하는 것이 이 설계안의 목적이다.

## 2. 현행 아키텍처 진단

```
업로드 → parse_uploads → run_review(규칙엔진, 순차) → [AI ON] ai_review(시트당 1회)
        → note_merge → notes_pipeline → _attach_references → 대시보드
```

**구조적 한계**

1. **순차·단일 관점** — 절차누락 → 4대중점 → 감리지적 → 계산 → 주석 → QC가 한 함수(`run_review`) 안에서
   순서대로 실행된다. 앞 단계의 판단 오류가 뒤 단계로 전파되며, 각 단계가 서로의 판단을 검증하지 않는다.
2. **계정 전문성의 부재** — `PROCEDURE_RULES`(9계정)를 벗어난 계정(무형자산, 법인세, 리스, 자본,
   특수관계자거래 등)은 KB 검색 결과에만 의존하여 "일반적인 기준 인용"에 그치고, 해당 계정 특유의
   함정(예: 재고자산 저가법 vs 진부화의 구분, 지분법 손상 지표, 리스 할인율 재검토 트리거)을 놓친다.
3. **AI 호출의 얕은 컨텍스트** — `ai_review`가 시트 단위로 호출되어 "이 시트가 다른 조서와 어떻게
   연결되는지"를 보지 못한다. 상호참조·대사 오류는 원천적으로 AI 시야 밖에 있다.
4. **검증자 없는 자기 판단** — 규칙엔진과 AI가 내린 판단을 다시 검증하는 단계가 없다. 오탐(불필요한
   지적)과 미탐(누락)이 같은 파이프라인 안에서 걸러지지 않고 그대로 출력된다.

이 진단은 「자가검토_작업지시서」의 §6 Gap표·§0.11 QC 3축 설계와 정합적이며, 본 설계안은 그 원칙을
**폐기하지 않고 멀티에이전트 구조 위에 재배치**한다.

<a id="3"></a>
## 3. 설계 원칙

| # | 원칙 | 설명 |
|---|------|------|
| P1 | **계정 전문화 (Account Specialization)** | 계정과목마다 전담 에이전트를 두어, 해당 계정의 표준감사프로그램·감리지적 패턴·계산 함정을 깊이 있게 판단 |
| P2 | **기능 분리 (Separation of Concerns)** | "합계검증", "상호참조", "절차완전성", "리스크사례매칭"은 계정과 무관하게 전체 조서셋을 가로질러 보는 별도 관점이므로 기능별 에이전트로 분리 |
| P3 | **병렬·독립 실행** | 모든 전문 에이전트는 서로의 산출물에 의존하지 않고 동시에 실행되며, 통합은 오케스트레이터 단계에서만 이루어짐 (레이턴시·비용 최소화) |
| P4 | **근거주의 (Zero-Hallucination Grounding)** | 모든 에이전트는 Hanul DB(RAG)에서 검증된 출처만 인용하며, 미확인 시 "근거 미확인"으로 표기 — 기존 기획서 원칙 1 계승 |
| P5 | **상호검증 (Cross-Validation)** | 계정 에이전트와 기능 에이전트의 findings는 반드시 상호 대조되며, 단일 에이전트의 단독 판단은 Tier1로 승격되지 않음 (§0.11 판정 트리 계승) |
| P6 | **오케스트레이터 최종 책임** | 중복 제거·충돌 해결·Tier 배정·3칸 리뷰노트 포맷팅은 오케스트레이터가 전담하며, 최종 산출물의 감사추적(audit trail)을 남긴다 |

## 4. 에이전트 카탈로그

### 4.1 오케스트레이터 — Lead Reviewer Agent (LRA)

| 항목 | 내용 |
|---|---|
| 페르소나 | 30년 경력 파트너급 심리역 — 최종 승인권자 |
| 역할 | 에이전트 스케줄링·산출물 통합·중복제거·충돌 조정·Tier 배정·리뷰노트 3칸 포맷팅(§0.0)·근거 재검증 |
| 입력 | 전 계정 에이전트 + 전 기능 에이전트의 Finding 목록(§6 스키마) |
| 출력 | 최종 리뷰노트 목록(대시보드·엑셀), 감사추적 로그, 골든셋 편입 후보 |
| 금지 | 근거(§6 `evidence_refs`) 없는 finding 승격 금지, 220자 초과 리뷰사항 문구 승격 금지(§0.0) |

### 4.2 기능별 에이전트 (Functional Agents) — 계정 무관, 조서셋 전역 관점

| ID | 명칭 | 목적 | 대응 Gap | 성격 |
|---|---|---|---|---|
| **FA-1** | 합계·계산검증 에이전트 (Tie-out & Calculation Agent) | 표 내 합계·부분합, Lead↔세부조서, FS↔주석, 전기대비 이상치 검증 | Gap#2 | **비AI·결정론적** — 수치 재계산만, RAG 미사용 |
| **FA-2** | 조서간 상호참조 에이전트 (Cross-Reference Agent) | `sheet_code_registry` 기반 Lead·세부조서·조회서·FS주석 간 참조 무결성 검증 | Gap#3, #16 | 결정론 + 경량 AI(주석 문구 대사) |
| **FA-3** | 표준감사프로그램 절차완전성 에이전트 (Audit Program Completeness Agent) | 계정별 필수절차 카탈로그(§B) 대비 **체크리스트 단위 Pass/Fail** 판정 | Gap#5, #6, #18 | 규칙 + AI(증빙 서술 판독) |
| **FA-4** | 4대중점·감리사례 리스크 에이전트 (Regulatory Focus & Enforcement-Precedent Agent) | 4대중점 체크리스트 Pass/Fail + 감리지적사례 **역매칭 선제 탐지** | Gap#9, #17 | RAG(정성) + 패턴매칭 |

**FA-1 합계·계산검증 에이전트 — 상세**

- 입력: `quantitative_extract`가 만든 `AmountGrid`/`AmountFact`, Lead 시트 총계, FS 계정별 잔액, 전기 비교열
- 판단 로직: (a) 표 내 합계=Σ(세부행) 오차 허용범위 내인지, (b) Lead 총계=세부조서 총계 일치 여부,
  (c) FS 본문 금액=주석 금액 일치 여부(Gap#3 주석 대사), (d) 전기대비 변동률이 사전 정의한 이상치
  임계값(예: ±30% 또는 중요성 기준액의 일정 비율)을 초과하는지
- 산출 예시: `"BB100 차입금 유형별 합계 12,450백만 ≠ BB Lead 12,380백만 (차이 70백만, PM의 3.2%)"`
- 특징: **RAG를 전혀 사용하지 않는 유일한 에이전트** — 「듀얼RAG 설계」의 "정량 = 추출·계산" 원칙을
  가장 순수하게 구현

**FA-2 조서간 상호참조 에이전트 — 상세**

- 입력: `SHEET_ROLE_REGISTRY`/`조서연결_대사_사전_FY2026.xlsx`(§D), 전체 업로드 조서의 시트맵
- 판단 로직: (a) `related_accounts`로 지정된 조서들이 실제로 모두 존재하는지, (b) `compare_unit`
  기준으로 지정된 두 시트의 수치가 대사되는지, (c) 주석 번호가 FS 주석과 실제 연결되는지,
  (d) 계속기업·특수관계자 등 **여러 조서에 걸쳐 언급되어야 하는 사항**이 한 곳에만 기재되어
  불일치하는지
- 산출 예시: `"CL100 제공보증 조회서 금액이 주석 27번 우발부채 공시금액과 상이"`

**FA-3 표준감사프로그램 절차완전성 에이전트 — 상세**

- 입력: `계정별_필수절차_카탈로그_FY2026.xlsx`(§B, procedure_id·required_evidence·detect_all/any·
  fail_if), 해당 계정 조서 전문
- 판단 로직: 키워드 1개 매칭이 아니라 **절차 단위**로 (a) `detect_all`에 명시된 키워드 **세트**가
  모두 존재하는지, (b) `required_evidence`에 명시된 증빙(조회서·tick·서명 등)이 실제로 첨부/기재
  되었는지, (c) `fail_if` 조건(예: "Ref만 있고 실제 대사 없음")에 해당하는지 — Pass/Fail을
  체크리스트 항목 단위로 산출 (Gap#5, #18 정면 대응)
- 계정 확장: 현재 9계정 → **4000 목차 전 계정**(Gap#6)으로 카탈로그를 확충해야 이 에이전트가
  전 계정에서 작동 — §4.3 계정 에이전트와 카탈로그를 공동 관리

**FA-4 4대중점·감리사례 리스크 에이전트 — 상세**

- 입력: `fss_focus` 체크리스트(L1~L4/U1~U4), `enforcement_case_learner`의 `red_flag_phrases`·
  `case_narratives`
- 판단 로직: (a) 4대중점 항목별 Pass/Fail(기존 `fss_focus` 로직 계승), (b) **조서 서술 내용 자체를
  감리지적사례의 red-flag 패턴과 직접 대조**하여, 기존 리뷰노트 존재 여부와 무관하게 선제
  지적(Gap#17 — 현행은 "노트 있을 때만 [사례인용] 보강") — 단, 계정·주제 이중 일치 조건(§0.9)을 유지하여
  오탐 방지
- Tier: 4대중점 Fail=Tier1, 감리사례 역매칭=Tier2~3 (신규 독립 지적이므로 오케스트레이터가
  근거 재검증 후 승격)

### 4.3 계정별 전문 에이전트 (Account Specialist Agents)

계정 에이전트는 "해당 계정만 아는 사람"의 역할이다. 각 에이전트는 자신이 담당하는 계정 조서 전체를
읽고, 그 계정에서 실무적으로 가장 자주 발생하는 오류·누락·감리지적 유형을 근거(KB)와 함께 짚어낸다.
아래 카탈로그는 K-IFRS/K-GAAP 감사에서 통상적으로 구분되는 14개 영역을 기준으로 하며, 기존
`조서연결_대사_사전`·4대중점 체크리스트에 이미 등장하는 계정을 우선 반영했다.

| ID | 계정과목 | 대표 조서코드 | 핵심 절차(요약) | 특이 리스크·중점 연계 |
|---|---|---|---|---|
| AA-01 | 현금및예금 | A, A Lead | 금융기관 외부조회·조회서 대사, 제한예금 분류 | §0.8 tick·Ref 인정 기준 |
| AA-02 | 매출채권·기타채권 | B, B Lead | 조회·연령분석·대손충당금 추정 근거 | 4대중점(건설·조선 매출채권비율) |
| AA-03 | 재고자산 | F1 | 실사입회·저가법(NRV)·진부화 판단 | 4대중점 L2/U2 재고 저가법 |
| AA-04 | 유형자산 | E | 감가상각 재계산·손상검사 트리거 | 신규 카탈로그화 필요(Gap#6) |

## 5. 협업 프로토콜 (오케스트레이션 흐름)

```
[업로드·파싱 완료 후]
                         ┌─────────────────────────────┐
Step 1  sheet_code_registry로 조서 → 계정 매핑          │  (결정론, 기존 코드 유지)
                         └──────────────┬────────────────┘
                                        │
              ┌─────────────────────────┼─────────────────────────┐
              ▼                         ▼                         ▼
    [계정 에이전트 병렬 기동]     [기능 에이전트 병렬 기동]      (둘 다 동시 실행,
    AA-01~AA-14 중 매핑된         FA-1 합계검증                  서로 의존하지 않음)
    계정만 활성화                  FA-2 상호참조
                                   FA-3 절차완전성
                                   FA-4 4대중점·감리사례
              │                         │
              └────────────┬────────────┘
                           ▼
             [Finding 목록 수집 — §6 스키마]
                           ▼
             Step 2  상호검증(Cross-Validation)
             - 동일 sheet_code·동일 category → 중복 후보로 그룹화
             - 계정 에이전트 finding ↔ FA-3 절차완전성 판정 대조
               (일치 시 병합·근거 보강 / 불일치 시 오케스트레이터 에스컬레이션)
             - FA-1·FA-2의 결정론적 finding은 별도 검증 없이 최우선 신뢰
                           ▼
             Step 3  Tier 배정 (§0.11 QC 3축 계승)
             - Tier1: 중대 절차 누락(FA-3 fail_if 발생) · 4대중점 Fail(FA-4)
             - Tier2: 계정 에이전트 단독 지적 + FA 교차확인 통과
             - Tier3: 감리사례 역매칭 신규 지적(FA-4, 근거 재검증 후)
             - 제외: 검토내역·결론 타당(§0.11.6), 문서화 존재(§0.11 §A-4)
                           ▼
             Step 4  근거 재검증(Zero-Hallucination Filter)
             - evidence_refs가 Hanul DB 실제 문서 ID와 매칭되지 않으면 강제 하향/제외
                           ▼
             Step 5  3칸 리뷰노트 포맷팅(§0.0) — 리뷰사항/리뷰근거/감리지적사례 각 필드 규격 적용
                           ▼
             Step 6  notes_pipeline 후처리(기존 유지) → 대시보드·엑셀 출력
                           ▼
             Step 7  골든셋 diff — 신규 지적 패턴 발견 시 골든셋 편입 후보로 로그
```

**설계 포인트**

- 계정 에이전트와 기능 에이전트는 **동일한 조서 데이터를 다른 렌즈로 동시에** 본다. 이는 실제
  회계법인에서 "계정 담당자가 절차를 수행하는 동안 QC 심리역이 별도로 합계를 재검산하는" 방식과
  동일하며, 어느 한쪽의 판단 오류가 다른 쪽에 의해 상쇄될 수 있다.
- **상호검증은 필수 관문이다.** 계정 에이전트 혼자만의 판단(예: "재고자산 진부화 검토 미흡")은
  FA-3(절차완전성)이 §B 카탈로그 기준으로 동일 결론을 내려야 Tier1로 승격된다. 단독 판단이
  곧바로 최고 중요도로 출력되는 것을 막아 오탐을 억제한다(P5).
- **FA-1·FA-2는 결정론적이므로 신뢰도 최상위**로 취급한다. AI의 서술적 판단보다 재계산 결과가
  우선한다는 원칙은 기존 「듀얼RAG 설계」§4.2와 완전히 정합적이다.

<a id="6"></a>
## 6. 공통 데이터 컨트랙트 (Finding 스키마)

모든 에이전트(계정·기능 불문)는 아래 JSON 스키마로 산출물을 반환한다. 오케스트레이터는 이 스키마
없이는 어떤 finding도 리뷰노트로 승격하지 않는다.

```json
{
  "agent_id": "AA-03 | FA-1 | ...",
  "agent_type": "account | functional | orchestrator",
  "sheet_code": "F1",
  "account": "재고자산",
  "category": "절차누락 | 계산오류 | 상호참조불일치 | 중점감리 | 감리지적유사",
  "severity_raw": "상 | 중 | 하",
  "finding_text": "220자 이내, §0.0 리뷰사항 규격 준수",
  "basis": "기준서/절차/사례 한 줄 인용",
  "to_be": "보완 조치 한 줄",
  "evidence_refs": ["KSA501", "FSS-2026-비상장-재고-03"],
  "confidence": 0.0,
  "cross_checked_by": ["FA-3"],
  "duplicate_group_id": null
}
```

| 필드 | 오케스트레이터 처리 규칙 |
|---|---|
| `evidence_refs` | 빈 배열이면 Tier1 승격 불가 — "근거 미확인"으로 강제 표기 |
| `cross_checked_by` | 계정 에이전트 finding은 최소 1개 기능 에이전트의 확인이 있어야 Tier1 승격 |
| `confidence` | 0.6 미만은 Tier3 이하로 자동 하향 |
| `duplicate_group_id` | 동일 sheet_code+category 그룹 내 최고 confidence 1건만 최종 출력 |

<a id="9"></a>
## 9. 품질 보증 — 골든셋·정밀도 관리

- **에이전트별 정밀도 지표:** 계정 에이전트·기능 에이전트 각각에 대해 Recall@Tier1(필수 지적 적중률),
  Precision(오탐 비율)을 독립적으로 측정한다. 오케스트레이터 통합 후 지표와 개별 에이전트 지표를
  비교해 "통합 단계에서 정보가 소실되는지"를 상시 점검한다.
- **골든셋 확장:** 현재 11개 케이스(4대중점 중심)에서 **14계정 × 최소 2케이스(오류조서/양호조서)**로
  확장 — 계정 에이전트가 실제로 작동하는지 계정 단위로 검증 가능해야 한다.
- **상호검증 로그:** `cross_checked_by`가 비어있는 Tier1 finding이 발생하면 회귀 실패로 간주 —
  단독 에이전트 판단의 무단 승격을 자동 탐지.
- **감사추적(Audit Trail):** 오케스트레이터의 병합·하향·제외 결정은 전량 로그로 남겨, 사후 QC가
  "왜 이 지적이 빠졌는가"를 역추적할 수 있어야 한다(현행 "0건 메시지 원인 미구분" Gap#8 해소).
