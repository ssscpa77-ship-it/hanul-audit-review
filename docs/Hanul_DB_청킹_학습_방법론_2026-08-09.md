## 1. 배경 및 목적

Hanul DB(3,069문서·43,355청크, 2026-08-09 기준)는 이미 색인이 되어 있으나, 그 색인은
**문서 구조를 전혀 인식하지 않는 고정길이 슬라이딩 윈도우**(`kb_extract.chunk_text`,
size=800자·overlap=120자)로 만들어졌다. 이 방식은 "청크 하나가 완결된 의미 단위인가"를
전혀 고려하지 않기 때문에, 검토 엔진(review_engine)·AI 리뷰(ai_review)·멀티에이전트가
근거를 인용할 때 다음과 같은 구조적 손실이 발생한다.

| 문제 | 구체적 사례 |
|---|---|
| 조문이 문단 중간에서 잘림 | 감사기준서 505(외부조회) 문단이 800자 경계에서 잘려, "충분한 확신을 얻지 못한 경우"까지만 인용되고 그 다음 문장(대체절차)이 별도 청크로 분리 |
| 출처 컨텍스트 소실 | 974페이지 통합본(`회계감사기준 전문(2025 개정).pdf`)을 그냥 800자씩 자르면, 어떤 감사기준서 몇 조인지 청크 안에서 알 수 없음 |
| 질의/회신 분리 | 질의회신 PDF가 800자를 넘으면 "Ⅰ. 질의 내용"과 "Ⅱ. 회신 내용"이 서로 다른 청크로 갈라져, 질의 없이 회신만 검색되는 경우 발생 |
| 여러 사례가 한 청크에 혼입 | 감리지적사례 모음 파일(예: `2018년 주요 감리지적 사례_.hwp`)에서 사례 A의 끝부분과 사례 B의 시작부분이 한 청크에 뒤섞임 |
| 조서 시트 경계 무시 | 감사조서 xlsx(`[시트: A]`, `[시트: BB,DD]` 등 여러 시트가 이어진 텍스트)를 문자 수로만 자르면 현금 시트 절차와 차입금 시트 절차가 한 청크에 섞임 |
| 구조화 데이터의 비구조화 | 자가검토_지침_템플릿 xlsx(계정별 필수절차 카탈로그 등)의 각 행(하나의 절차 레코드)이 셀 구분자 없이 공백으로 뭉쳐져, "저가법" 검색 시 procedure_id·basis 등 필드를 구분할 수 없음 |

이 문서는 (1) 카테고리별 구조인식 청킹 지침을 구체적으로 정의하고, (2) 이를 실제
코드(`chunking_strategy.py`)로 구현하고, (3) 실제 자료로 실행·검증한 결과를 기록한다.

## 2. 청킹 원칙

| 원칙 | 설명 |
|---|---|
| P1. 구조 우선 | 문서가 가진 자연 경계(조항 번호·Q/A 마커·사례 제목·시트 마커·행 구분)를 최우선으로 인식하고, 그 경계 안에서만 문자 수 기준으로 묶는다. 경계를 넘어 자르지 않는다. |
| P2. 의미 단위 보존 | 문단(또는 행) 하나가 목표 크기보다 커도 억지로 자르지 않는다 — 조항 하나가 조금 길어도, 조항이 반으로 잘리는 것보다 낫다. |
| P3. 출처 컨텍스트 prefix | 모든 청크 앞에 `[문서명 — 소단위]` 형태의 출처 태그를 붙인다. 청크가 검색 결과로 단독 노출되어도 어떤 기준서·조서·사례인지 즉시 식별 가능해야 한다. |
| P4. 카테고리별 차등 | "정성적 서술"(기준서·질의회신·감리사례)과 "구조화 레코드"(자가검토 지침 템플릿)와 "혼합형"(감사조서: 서술+수치)은 서로 다른 전략이 필요하다 — 「듀얼RAG 설계」의 정성/정량 이원화 원칙과 정합. |
| P5. 안전한 폴백 | 카테고리를 인식하지 못하거나 청커가 예외를 던지면, 기존 슬라이딩 윈도우로 자동 폴백한다 — 청킹 개선이 색인 실패로 이어지지 않도록 한다. |

## 4. 구현

### 4.1 신규 모듈 `chunking_strategy.py` (hanul-002)

카테고리 → 청커 함수를 매핑하는 디스패처(`chunk_for_category(category, text, title)`)와
6개 전용 청커(`chunk_standards`, `chunk_qna`, `chunk_enforcement`, `chunk_focus`,
`chunk_workpaper`, `chunk_guideline`)로 구성했다. `build_index.py`는 기존
`ke.chunk_text(text)` 호출을 `cs.chunk_for_category(category, text, title)`로
한 줄만 교체했다 — 색인 파이프라인의 나머지 구조(추출·중복검사·DB 저장)는 변경하지
않았다.

### 4.2 `kb_extract.py` 소폭 개선

`_excel_openpyxl`의 행 내 셀 구분자를 공백(`" "`)에서 `" | "`로 변경했다 — 계정별
필수절차 카탈로그 같은 구조화 xlsx에서 필드 경계가 검색 결과에 그대로 드러나도록 했다
(§3.1 카탈로그 청크 예시 참조). 이 한 글자 변경이 §3의 "구조화 데이터의 비구조화"
문제를 상당 부분 해소한다.

### 4.3 `build_index.py` 문서당 청크 상한 상향

기존 `_MAX_CHUNKS = 400`은 800자 슬라이딩 윈도우 기준으로 설정된 값이다. 구조인식
청킹은 조항 단위(평균 434자)로 더 촘촘하게 나누므로, 974페이지 통합본(`회계감사기준
전문`) 같은 대용량 문서에서 400 상한에 걸려 후반부 기준서(700호대·1100/1200호대)가
누락되는 것을 확인했다(§5.1). `_MAX_CHUNKS`를 **3,500**으로 상향해 이 문제를 해소했다.

## 5. 실행·검증 결과

이번 세션에서는 클라우드 샌드박스(디바이스 브리지의 Linux VM)에서 실제 Hanul DB 원본
파일을 읽어 청킹 결과를 직접 검증했다(운영 중인 `kb_store/hanul_kb.sqlite`는 건드리지
않음 — §6 참조).

### 5.1 회계감사기준 전문(2025 개정).pdf — 974페이지 통합본

| 항목 | 기존(슬라이딩 윈도우) | 신규(구조인식) |
|---|---|---|
| 청크 수 | 400(상한에 걸림 — 후반부 손실) | **2,985**(상한 미도달, 전체 커버) |
| 평균 청크 길이 | 800자(고정, 문장 잘림 가능) | 434자(조항 경계 보존) |
| 감사기준서 700 이후 커버 | ❌ (상한 400 이전에 잘림) | ✅ 254개 청크로 확인 |
| 출처 식별 가능성 | 청크 텍스트만으로는 불가 | 매 청크에 `[... — 감사기준서 NNN '제목']` prefix |

실제 산출 청크 예시(문단 3, 4):

```
[회계감사기준 전문(2025 개정) — 감사기준서 200 '독립된 감사인의 전반적인 목적...']
3. 감사의 목적은 의도된 재무제표 이용자의 신뢰수준을 향상시키는 데 있다. ...
```

### 5.2 질의회신 — `[GKQA01-122] 판매장려금의 처리에 관한 질의.pdf`

기존 방식과 신규 방식 모두 1청크로 귀결(원문이 800자보다 짧음)되나, 신규 방식은
`[질의회신: 제목]` prefix를 붙여 이 청크가 어떤 질의인지 검색 결과에서 즉시 드러난다.
장문 질의회신(첨부 서술이 긴 경우)에서는 기존 방식이 "Ⅰ. 질의 내용" 중간에서 잘라
"Ⅱ. 회신 내용"과 무관한 두 청크를 만드는 반면, 신규 방식은 회신 경계에서만 분리한다.

### 5.3 한울 예시조서 — `4000_계정별 실증절차_FY2026_소규모_v1.xlsx`

| 항목 | 결과 |
|---|---|
| 원본 텍스트 | 74,899자, 시트 다수(4000 실증절차 CS·AR-수행단계양식·A·BB,DD 등) |
| 신규 청크 수 | 110개 — **시트 경계를 한 번도 넘지 않음** (검증: `[시트: BB,DD]` 청크에 차입금 절차 7개 항목이 온전히 포함, 인접 시트인 A(현금) 내용 혼입 없음) |
| 절차 항목 완전성 | "3. 외부 조회에 대한 구체적인 절차는 Audit Guide 3320 외부조회를 참고한다." 같은 번호+어서션 태그(E, RO, C, A 등) 형식이 한 줄 안에서 훼손 없이 보존됨 |

### 5.4 계정별 필수절차 카탈로그_FY2026.xlsx (신규 확충본, 15계정·28절차)

29개 청크(헤더 1 + 데이터 28) — **행 하나 = 절차 하나 = 청크 하나**로 정확히 대응.
`" | "` 구분자 적용 후 예시:

```
[계정별_필수절차_카탈로그_FY2026 — 필수절차] 매출채권 | B-01 | 매출채권 외부조회 |
잔액>PM | 조회서;회신;대사 | 조회 | confirmation;조회서 | 일치 또는 차이 해소 | C |
Ref만 있고 조회서 회신 없음 | KSA505 | 미회신 거래처 대체절차(입금확인·후속거래) 수행 근거 보완
```

이 형태는 FTS 검색에서 "Ref만 있고" 같은 fail_if 문구, "KSA505" 같은 근거 문구를
독립적으로 정확히 매칭할 수 있게 한다 — 멀티에이전트(FA-3·계정 에이전트)가 근거를
인용할 때 이 정밀도가 그대로 리뷰노트 품질로 이어진다.

## 6. 실제 전체 재학습 실행 — 왜 지금 실행하지 않았는가, 어떻게 실행할 것인가

### 6.1 이번 세션에서 전체 색인을 재생성(--reset)하지 않은 이유

세션의 디바이스 브리지(Linux 샌드박스)는 **읽기 검증용**으로만 사용했고, 운영 중인
`kb_store/hanul_kb.sqlite`(3,069문서·43,355청크)를 실제로 재생성하지는 않았다.
이유는 다음과 같다.

1. **네트워크 차단** — 이 샌드박스는 외부 네트워크에 접근할 수 없어 `pip install`이
   불가능하다. `fastembed`(임베딩), `olefile`(.hwp 파싱), `xlrd`(구버전 .xls)가
   설치되어 있지 않다.
2. **.hwp·.xls 손실 위험** — 금융감독원·한국공인회계사회 감리지적사례의 상당수가
   `.hwp`이다. `olefile` 없이 재색인하면 이 파일들이 전부 "내용없음(empty)"으로
   기록되어, **현재 이미 잘 색인된 480여 건의 hwp 감리지적사례 텍스트가 사라진다.**
   이는 개선이 아니라 퇴보이므로, 이 환경에서는 `--reset`을 실행하지 않았다.
3. **실제 venv와 분리된 환경** — `hanul-002/VENV`는 macOS 네이티브 Python
   프레임워크를 참조하므로 이 Linux 샌드박스에서 실행할 수 없다. 실제 운영 환경(Mac)
   에서 실행해야 OCR·hwp·임베딩까지 포함한 완전한 재학습이 보장된다.

### 6.2 대표님께서 실행하실 명령 (Mac, `hanul-002` 폴더에서)

```bash
cd hanul-002
source VENV/bin/activate
```

### 6.3 단계적 접근을 원하시는 경우

한 번에 전체를 재생성하는 대신, 카테고리 영향이 가장 큰 「회계감사기준」 폴더부터
`--path` 옵션으로 검증할 수 있다.

```bash
VENV/bin/python build_index.py --reset --path "/Users/admin/Desktop/Hanul DB-SSS/회계감사기준"
```

단, `--reset`은 DB 전체를 삭제하므로 폴더별 단계적 재생성에는 적합하지 않다 —
전체 재생성 전 **소규모 검증**이 필요하면 `--limit 30`으로 임의 30건만 먼저 확인하는
것을 권장한다.

   패턴(번호+한글, "사례 N" 등)을 기준으로 했다. 재색인 후 `.hwp` 모음 파일이 실제로

   패턴이 있으면 `chunking_strategy.chunk_enforcement`의 `_CASE_BOUNDARY_RE`를
   보강하는 것을 권장한다.

   대비 하이브리드 검색의 Recall/Precision을 비교해, 구조인식 청킹이 실제 리뷰노트
   근거 인용 품질에 미치는 영향을 정량화할 것을 권장한다(듀얼RAG 설계 §5 방식 재사용).
