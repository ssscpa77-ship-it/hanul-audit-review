동일 내용을 `hanul-002/data/templates/`의 로컬 백업본에도 반영했다(클라우드 배포 시 Hanul DB
미마운트 상황의 폴백용).

## 2. 왜 app.py를 건드리지 않았는가

작업 착수 시점(2026-08-09) `git status`에 `app.py`, `enforcement_review.py`,
`output_formatter.py`, `docs/자가검토_작업지시서_전체설정.md`, `share/exports/latest_review.xlsx`가
**다른 협업자(Cursor)의 미커밋 변경사항**으로 남아 있었다(리뷰노트 3칸 설계 반영 작업).
충돌·덮어쓰기 위험을 피하기 위해 이번 라운드는 **신규 파일만 추가**하는 방식으로 구현했고,
기존 `review_engine.run_review()` 파이프라인은 한 줄도 변경하지 않았다
(`golden_set_regression.py` 11/11 통과로 무영향 확인됨).

## 3. 사용법 (현재 — 독립 실행)

```python
import agent_orchestrator as orch
from parser import ParsedDocument  # 실제 업로드 파싱 결과

doc = parse_uploads(...)  # 기존 app.py 파싱 로직 재사용
result = orch.run_multi_agent_review(doc)

result["findings"]          # 최종 Finding 목록 (importance/category/defect/... 필드 포함)
result["audit_trail"]       # 승격·하향·중복제거 로그
result["tier_counts"]       # {"상": n, "중": n, "하": n}
```

스모크 테스트: `python3 agent_orchestrator.py` (합성 조서 2건으로 파이프라인 동작 확인,
재고자산 NRV·진부화 절차 누락을 정확히 잡아내는지 검증됨).

## 4. app.py 통합 방법 (검토 후 착수 권장 — Phase 4)

1. Cursor의 3칸 리뷰노트 작업을 먼저 커밋·정리한다.
2. `app.run_analysis()`에서 `run_review()` 호출 다음에 아래와 같이 추가:
   ```python
   if os.getenv("MULTI_AGENT_REVIEW") == "1":
       ma_result = agent_orchestrator.run_multi_agent_review(doc, mat, is_listed, engagement)
       notes += ma_result["findings"]
   ```
   환경변수로 토글해 기존 파이프라인과 나란히(A/B) 검증할 수 있게 한다(`ab_experiment.py`의
   variant 개념과 동일한 패턴).
3. `note_merge.merge_review_notes()`가 `agent_id`/`evidence_refs` 등 신규 필드를 그대로
   통과시키는지 확인 — 기존 필드만 사용하는 로직이라면 별도 수정 없이 동작할 것으로 예상되나,
   병합 단계에서 `source` 필드(`"agent:FA-3"` 등)를 기준으로 한 특수 처리가 필요하면 보완.
4. `golden_set_regression.py`에 계정별 케이스(§9 품질보증 — 14계정×2케이스) 추가 후
   `MULTI_AGENT_REVIEW=1`로 재실행해 회귀 확인.

## 5. 알려진 제약 (다음 보완 대상)

- FA-2(상호참조)는 현재 기존 `_check_note_references`/`_check_cross_fs_totals`/
  `_check_contingency_confirmations`를 재포장한 수준 — §D 조서연결_대사_사전의
  `compare_unit`·`related_accounts` 기반 신규 로직(설계안 §4.2 FA-2 상세)은 미구현.
- 계정 에이전트는 AA-01·AA-03만 계정 고유 함정 로직을 갖고, 나머지 12개 계정은
  카탈로그 기반 공통 로직(`_generic_risk_scan`)으로 동작 — 카탈로그의 "특이 리스크" 서술이
  풍부해질수록 자동으로 정교해지나, 계정 고유 로직(예: 지분법 손상지표 자동판단)은
  추가 구현이 필요.
- 감리사례 역매칭(FA-4, Gap#17)은 `red_flag_phrases` 단순 포함 여부만 검사 —
  문맥 유사도 기반 매칭(임베딩)은 Phase 5(설계안 §8) 대상.
- `계정별_필수절차_카탈로그_FY2026.xlsx`의 `cross_sheet` 코드를 `sheet_code_registry`
  실제 매핑(A/C/E100/G/H/SAJ/BB/CL/FF/GG/P·Q/T/L 등)에 맞춰 정정했으나, 상장/비상장
  변형(variant)별 코드 차이는 반영하지 않았다(상장 변형 기준만 적용).
